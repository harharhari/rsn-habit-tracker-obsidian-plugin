## C. Recommended source update with Git

Use a fresh clone or a clean working copy. Preserve its .git directory when copying supplied files. The following branch name is an example; choose another if it already exists.

```text
git clone https://github.com/harharhari/rsn-habit-tracker-obsidian-plugin.git
cd rsn-habit-tracker-obsidian-plugin
git status --short
git switch -c codex/update-1.1.10
```

Copy the CONTENTS of the delivered repository/ into this clone, including hidden files. Do not use a delete-all or mirror-with-delete command. Inspect obsolete tracked files:

```text
git ls-files -- src/core.js src/plugin-source.js
```

If both paths are listed, remove them from the update branch with git rm -- src/core.js src/plugin-source.js. If only one is listed, remove only that path; if neither is listed, skip. Inspect any accidentally tracked generated folders before explicitly untracking/removing them. Do not use git clean or reset as a bulk cleanup shortcut.

Install Node.js 22+ and npm for development, then run:

```text
npm ci --ignore-scripts
npm run check
npm run test:helper
```

Python helper tests need Python; Windows also needs tzdata. See GITHUB-AND-COMMUNITY-RELEASE.md. Normal plugin users need neither npm nor Python.

Review git status --short and git diff --stat. In this dedicated clean update branch, stage the intended changes, inspect them and commit:

```text
git add -A
git diff --cached --stat
git diff --cached --name-status
git commit -m "Update plugin source and deployment guidance for 1.1.10"
git push -u origin codex/update-1.1.10
```

Open a pull request into the actual default branch. Wait for Ubuntu, Windows and macOS checks, inspect changes, then merge. If you use a working copy with other changes, stage only this update instead of git add -A. Do not force-push over history.

## E. Deploy the manual kit to GitHub — recommended CI artifact route

You do NOT need to upload manual-downloads/ manually. The supplied .github/workflows/ci.yml builds equivalent files and uploads release/ as a workflow artifact for each OS. This keeps generated downloads out of source and out of the Community release.

1. Push/merge the complete source and open Actions → Build and review.
2. Open the successful run for the intended commit; confirm the displayed commit SHA/version.
3. Wait for all three jobs. On the run summary, find Artifacts.
4. Download habit-calendar-test-kit-Linux (or Windows/macOS). The runtime is portable, so use one matching kit rather than mixing files from different runs.
5. Extract the GitHub artifact ZIP. Its six files are main.js, manifest.json, styles.css, hex-color-list.md, rsn-habit-calendar-one-b-1.1.10.zip and SHA256SUMS. If the client adds an outer directory, enter the directory containing these files.
6. Verify its SHA256SUMS using CHECKSUMS.md. This checks five payloads, excluding the checksum file itself.
7. For installation, extract the INNER rsn-habit-calendar-one-b-1.1.10.zip and place its plugin folder in the vault's .obsidian/plugins/. Alternatively copy just main.js, manifest.json and styles.css into the correct plugin folder. Do not copy the entire artifact wrapper into Obsidian.

Optional GitHub CLI download:

```text
gh run download RUN_ID --repo harharhari/rsn-habit-tracker-obsidian-plugin --name habit-calendar-test-kit-Linux --dir manual-kit-1.1.10
```

Replace RUN_ID with the intended successful workflow run ID. The artifact route needs a signed-in GitHub account with repository read access. Artifacts expire according to the repository retention policy (90 days by default), so they are suitable for maintainer/testing distribution, not the primary permanent public download. See [GitHub artifact-download instructions](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts).

The optional kit ZIP is not automatically attested. The separate release workflow attests the three loose Community assets it actually publishes to its draft. Do not describe all CI artifacts or the inner ZIP as signed merely because they were built by Actions.

## F. Optional permanent manual downloads

For ordinary users, recommend the three files on the plugin's normal GitHub release, or the Community installer after acceptance. These are sufficient; a separate manual kit is not necessary.

If you specifically want permanent, anonymous public access to the full six-file kit, use a SEPARATE downloads-only repository, for example harharhari/rsn-habit-tracker-downloads. This is a suggested name, not a repository created by this work. Do not register that downloads repository as the Obsidian plugin repository.

1. Create the separate repository on GitHub. Keep it private while testing if desired; anonymous downloads require it to be public. Include a README linking to the plugin source repository, license and installation guide.
2. Create a release there with a distinct descriptive tag such as manual-kit-1.1.10. Identify the exact plugin version and source commit in its description.
3. Attach the SIX files from one verified manual-downloads folder or one successful CI artifact individually. Do not attach a directory object; select its six files under Attach binaries. Do not mix the local handoff kit and workflow files unless their full checksums match.
4. Make GPL source availability explicit: link to the corresponding immutable source tag/commit in the plugin repository and keep that source available. The inner installation ZIP contains LICENSE and NOTICE; the downloads README should identify GPL-3.0-only and author harharhari.
5. Download the six attachments into a fresh directory, check SHA256SUMS and test installation. If using a kit built separately from the attested release, do not claim the ZIP itself has provenance. Prefer the official three-asset release for users wanting the attested binaries.
6. When public, link this optional manual-kit release from the plugin README/documentation as a separate convenience download. Keep the plugin's own Community release limited to the supported three assets.

Do not create a second convenience release in the plugin repository solely to host extras: it can confuse version discovery and the review process. Do not commit generated manual-downloads to the main source tree merely to make them downloadable. The CI artifact route already serves testers; a separate downloads repository is optional overhead, not required deployment.

If you have already published different code under 1.1.10, do not overwrite that tag or its signed binaries. Increment the version for subsequent runtime changes. If a 1.1.10 tag exists but has no release, first confirm it contains the intended runtime and release-note files. The workflow can build that existing tag while using the committed workflow on the default branch. Documentation-only updates can remain on the default branch without moving the old tag. New workflow functionality should be reviewed before use.

Keep the existing ID rsn-habit-calendar-one-b and name rsn habit calendar one b. Return to the existing directory entry for the new review; do not create a duplicate plugin. ## H. Install or upgrade Obsidian

For Windows, Ubuntu, Mac and accessible Android vaults: back up the vault, close Obsidian, create .obsidian/plugins/rsn-habit-calendar-one-b/ if absent and copy the three program files directly inside. Reopen, enable the plugin, verify 1.1.10 and run Open current month. Use rsn-test-vault first.

On an existing 1.1.3/1.1.4 installation, preserve data.json and the ENTIRE Habit Tracker folder, including custom colors, Records, Statistics and System. Replace program files only. The optional starter color file from a kit must not overwrite the user's customized vault color note. Do not accept a current-month reset just to install an update.

For iPhone/iPad, use the documented desktop-to-device Obsidian Sync route first, or Mac-assisted copying into a separate iCloud vault. Do not combine Sync and iCloud on the same vault. After Community acceptance, use Settings → Community plugins → Browse → install/enable on each platform. INSTALL-DOWNLOAD.md and the PPT contain platform steps.
